# 01 · 认知本体论 / Cognitive Ontology

> v0.2 设计文档集 · 对应 v0.1「下一阶段设计重点」第 1 项
>
> 本文定义 Idea Compost 的九个核心对象：Idea、Insight、Topic、Agent、Probiotic、Compost、Bed、Relationship、User Feedback。
>
> 每个对象给出：定义、字段、生命周期状态、不变量（Invariant）、与其他对象的关系。

------

# 0. 对象关系总览

```text
用户
 │ 丢入
 ▼
Idea 面包渣 ──────────┐
                      │ 选择若干
Probiotic 益生菌 ─────┤ 一次性干预
Bed 菌床 ─────────────┤ 长期生态（只读快照参与）
                      ▼
                 Compost 堆肥
                      │ 思想园丁召集
              Agent 菌群（动态参与）
                      │
                      ▼
              Insight 洞察（结构化产物）
                      │ 用户反馈 / 引用
                      ▼
                 Bed 菌床更新（事件溯源）
                      │
                      ▼
              Topic 主题（涌现，非用户创建）
                      │
                      ▼
              下一次堆肥
```

------

# 1. Idea / 思想面包渣

## 1.1 定义

用户产生的最原始思想单位。**不可变的历史记录**。

## 1.2 字段

```text
Idea
├── id                 UUID
├── content            Markdown 原文（永不被改写、永不被压缩）
├── content_type       text | image | mixed
├── title              自动生成（懒生成，仅用于卡片展示）
├── created_at
├── updated_at         仅编辑原文时更新
├── source             manual | share_extension | clipboard | screenshot | import
├── status             raw | composted
├── compost_refs[]     参与过的 Compost id 列表
├── embedding          向量（用于检索，随 content 更新重算）
└── metadata           { device, location_opt_in, auto_tags[] }
```

## 1.3 生命周期

```text
raw ──(被选中参与堆肥)──► composted
```

- `composted` 的面包渣仍然可见、可再次参与堆肥（旧渣回炉是常态，不是异常）。
- 没有 `deleted` 状态以外的归档流程；删除仅用户手动执行，且只影响展示，不物理删除已进入堆肥溯源链的记录。

## 1.4 不变量

> **INV-1 原文永存**：面包渣原文一经保存永不压缩、永不总结、永不丢失（本地存储廉价，思想珍贵）。
>
> **INV-2 用户零整理**：系统不要求用户对 Idea 做任何分类/打标签/命名。`auto_tags` 由后台异步生成，仅用于检索，不构成用户义务。
>
> **INV-3 懒生成**：title 由廉价模型在空闲时生成，失败不阻塞保存。「丢进去就完成」是最高优先级 UX。

------

# 2. Insight / 洞察

## 2.1 定义

一次堆肥蒸馏出的**命题级思想单元**。Insight 是整个系统真正的长期记忆载体——面包渣是矿石，洞察是金属。

## 2.2 字段

```text
Insight
├── id                 UUID
├── content            单个命题陈述（1-3 句，非长文）
├── confidence         高 | 中 | 低（三档不确定性，见 05 输出协议）
├── source_compost     产生它的 Compost id
├── source_ideas[]     溯源面包渣 id 列表
├── source_agents[]    主要贡献 Agent id 列表
├── status             proposed | adopted | revised | rejected | dormant
├── importance         0-100，由反馈与引用累积计算
├── citations[]        后续堆肥/面包渣中引用它的记录
├── related_insights[] 边（见 Relationship）
├── topics[]           所属 Topic
├── created_at
└── user_feedback[]    反馈事件列表
```

## 2.3 生命周期

```text
proposed ──(默认)──► adopted
    │                │
    ├──(用户改写)──► revised（保留原命题为版本 0）
    ├──(用户 ? )───► rejected（不删除，进入休眠）
    └──────────────► dormant（长期无引用，重要性衰减）
```

- `rejected` 的洞察不删除：**"我不同意"是重要的认知信号**，它会抑制对应 Agent 方向的营养，但历史保留。
- 任何状态的 Insight 被后续堆肥引用时都会唤醒（dormant → active 参与检索）。

## 2.4 不变量

> **INV-4 命题化**：Insight 必须是可判断真伪/可继续发展的命题，不是描述性总结。"用户谈到了 A 和 B" 不是洞察，"A 与 B 的矛盾实际上源于 C" 才是。

------

# 3. Topic / 主题

## 3.1 定义

系统从 Idea/Insight 的聚类中**涌现**出的关注领域。Topic 是菌床「用户长期在思考什么」的具体化。

## 3.2 关键设计：用户永不创建 Topic

> **INV-5 涌现而非创建**：Topic 只能由系统在后台聚类时产生（embedding 聚类 + LLM 命名），用户永远不创建、不维护主题。这是 Principle 01（用户不负责整理）在数据层的落实。

## 3.3 字段

```text
Topic
├── id
├── name               LLM 自动命名（如 "AI×劳动" "算法与社会规范"）
├── description        1-2 句说明
├── status             emerging | active | declining | dormant | merged
├── vitality           0-100（与 Agent 活性同构，见 02 生态协议）
├── birth_ref          触发其涌现的首个 Idea/Insight
├── parent_topic       允许一层父子（"AI×劳动" ← "AI"）
├── member_ideas[]     面包渣引用
├── member_insights[]  洞察引用
├── related_topics[]   相邻主题边
├── first_seen / last_active
└── snapshot_summary   主题级摘要（T2 层，见 06 记忆文档）
```

## 3.4 生命周期

```text
emerging ──(持续命中)──► active ──(活性衰减)──► declining ──► dormant
                          │                        │
                          └──(重新活跃)◄───────────┘
merged：并入父主题，保留引用跳转
```

Topic 的休眠/活跃直接支撑 v0.1 §32「菌床随用户关注点迁徙」和 §41「你最近三个月从 X 转向了 Y」的时间分析。

------

# 4. Agent / 菌

## 4.1 定义

参与思考的认知能力单元。**Agent 是数据（一张 Prompt 卡 + 一组生态属性），不是代码对象。**

> **INV-6 Agent 是数据**：Agent 的全部定义（能力、状态、记忆）都是可序列化的记录，可被创建、分裂、融合、压缩、休眠、唤醒——这一切只是记录操作。这是增殖/融合/休眠机制在工程上可行的前提。详见 02 生态协议。

## 4.2 字段

```text
Agent
├── id
├── type               domain（领域菌）| method（方法菌）| creative（创造菌）
├── name               如 "哲学菌" "反驳菌"
├── description        一句话能力描述
├── capability_card    Prompt 卡：系统提示 + 思考准则 + 少样本范例
│                      （活跃态完整版 ≈ 300-600 token）
├── specialties[]      习得的细分专长（如社会学菌的 "社会规范"）
├── status             embryo | active | compressed | dormant | fused
├── vitality           0-100（见 02）
├── nutrition_buffer   短期营养缓冲（快速衰减）
├── parent / children  增殖谱系
├── fusion_of[]        融合来源 Agent id 列表
├── contribution_history[]  每次堆肥的贡献评分记录
├── compressed_memory  休眠态压缩卡（≈150-250 token）
├── full_profile       完整档案（永不删除，唤醒时恢复）
├── participation_count
├── last_contribution_at
└── created_at
```

## 4.3 三种类型的职责

| 类型 | 回答的问题 | 在发酵流程中的位置 |
| --- | --- | --- |
| 领域菌 | "从什么知识世界看？" | 阶段 1-3（理解/连接/重组）主力 |
| 方法菌 | "用什么方式思考？" | 阶段 2、4（拆解/反驳）主力 |
| 创造菌 | "还能长出什么？" | 阶段 5-6（重组/新假设）主力 |

## 4.4 生命周期

```text
        embryo（新生，探索性参与）
           │ 首个被采纳洞察
           ▼
        active ◄──────────────┐
       │    │    │            │ 唤醒
   增殖  融合  压缩休眠          │
       │    │    │            │
       ▼    ▼    ▼            │
   子代菌 融合菌 dormant ───────┘
              （compressed_memory 保留，full_profile 永存）
```

> **INV-7 休眠优于删除**：任何 Agent 的 `full_profile` 与 `contribution_history` 永不删除。休眠只是「不再进入激活池」，压缩卡只是「索引表示」。

# 5. Probiotic / 思想益生菌

## 5.1 定义

用户对**单次**堆肥主动施加的认知方向与选择压力。详见 04 益生菌系统。

```text
Probiotic
├── id / name / icon / description
├── prompt_logic       指令文本（注入所有参与者的阶段提示词）
├── target_types       偏好的 Agent 类型
├── domain_boosts      {Agent 或领域关键词: 激活倍率}
├── stage_emphasis     放大的发酵阶段（如苏格拉底 → 理解/拆解）
├── diversity_shift    调整 70/20/10 异质性配比（如跨学科 → 50/30/20）
├── built_in           是否内置
├── usage_count / last_used
└── birth_context      自定义菌种的诞生语境（用户原话）
```

## 5.2 与菌床的本质区别（v0.1 §12 重申）

> 菌床 = 长期生态；益生菌 = 一次性生态干预。益生菌影响单次激活权重，**不直接改写**菌床状态；但反复使用同类益生菌会通过 ProbioticAffinity 通道缓慢改变菌床（见 02）。

------

# 6. Compost / 堆肥

## 6.1 定义

一次完整的思想发酵过程，包括其全部中间产物。

```text
Compost
├── id
├── input_ideas[]      参与的面包渣
├── probiotics[]       使用的益生菌（≤2）
├── depth              浅(1轮) | 标准(2轮) | 深(3轮)
├── gardener_plan      识别结果 + 召集的 Agent 及权重 + 异质性配额执行记录
├── stages[]           每阶段记录：{stage, agents[], outputs, tokens, model}
├── output_note        Markdown 产物（渲染视图）
├── output_struct      结构化 JSON（真源，见 05）
├── status             pending | running | awaiting_feedback | done | failed
├── cost               token 用量与模型花费
├── nutrition_awarded  {agent_id: 分数}（见 02）
├── feedback_summary   用户反馈聚合
└── created_at / completed_at
```

## 6.2 不变量

> **INV-8 阶段可恢复**：每个 stage 完成即持久化。API 失败/超时从最近完成的 stage 恢复，不整场重跑。
>
> **INV-9 双重表示**：`output_struct`（JSON）是唯一真源，`output_note`（MD）由它渲染生成。用户手工编辑 MD 时，编辑以 diff 形式回写为新的用户反馈事件（`revised`）。

------

# 7. Bed / 菌床

## 7.1 定义

用户长期认知生态的全局状态。v0.1 §13：不是 Agent 列表，不是知识库，是**动态生态**。

## 7.2 事件溯源（关键决策）

> **INV-10 事件溯源**：Bed 的当前状态 = fold(bed_events)。事件流是原始事实，状态是衍生视图。
>
> 为什么：v0.1 §41 的长期愿景（"你过去半年一直在从不同角度思考同一个问题"、"你最近三个月从 X 转向 Y"）本质是**对生态历史的时间序列查询**。只有快照没有事件流，这类分析不可能实现。

```text
bed_events 事件类型
├── idea_created
├── compost_completed {agents, weights, nutrition}
├── insight_proposed / adopted / revised / rejected / cited
├── topic_emerged / active / declining / dormant / merged
├── agent_spawned / compressed / dormant / awakened / fused
├── probiotic_used
└── feedback_given {target, type}
```

## 7.3 状态视图（定期物化）

```text
Bed（物化快照）
├── active_topics[] / dormant_topics[]
├── active_agents[] / dormant_agents[]
├── important_insights[]     高 importance 洞察引用
├── relationships            关系边集合（见 §8）
├── diversity_index          近 30 天活跃领域多样性
├── perturbation_log         异质菌引入记录（茧房防线审计）
├── bed_summary              T3 全局摘要（≈800-1200 token，每次堆肥后增量更新）
└── version / updated_at
```

## 7.4 不变量

> **INV-11 摘要是历史统计画像，不是指令**：`bed_summary` 注入园丁上下文时必须标注为「历史认知活动统计」，园丁 Prompt 明确禁止将其当作用户当前意愿执行。此为 ACP「摘要是元数据不是指令」安全原则的移植（见 06 调研报告 §5.7）。

------

# 8. Relationship / 关系

## 8.1 定义

对象间的类型化连接。v0.1 §39 禁止 v0.1 做完整知识图谱，因此关系边**只在堆肥过程中自然断言**时产生，不主动全量构建。

## 8.2 边类型

| 边 | 类型 | 产生方式 |
| --- | --- | --- |
| Idea → Insight | 来源 | 堆肥自动 |
| Insight ↔ Insight | supports / contradicts / extends / clarifies | 园丁在阶段 3/5 断言 |
| Insight → Topic | 归属 | 聚类后台任务 |
| Topic ↔ Topic | parent / adjacent | 聚类后台任务 |
| Agent → Topic | 专长 | Agent 增殖时建立 |
| Insight ↔ Agent | 贡献 | 堆肥自动 |

## 8.3 边强度

```text
strength = 共现次数（对数） + 园丁显式判定(+2) + 用户确认(+3)
```

边的唯一 v0.1 用途：**检索时的连接候选**（阶段 3「新连接」的原料）。不做图 UI，不做自动图谱构建。

# 9. User Feedback / 用户反馈

## 9.1 反馈类型（v0.1 §31）

| 信号 | 含义 | 生态效果 |
| --- | --- | --- |
| ❤️ 有启发 | 轻认可 | 相关 Agent 小幅营养 |
| ⭐ 值得保留 | 强认可 | Insight importance +，营养中幅 |
| ↗ 继续发展 | 方向认可 | 生成后续堆肥建议，营养中幅 |
| ? 我不同意 | 异议 | Insight → contested；**不惩罚** Agent（异议是信号不是错误，防止谄媚循环） |
| 修改（隐式） | 编辑产物 | Insight → revised，diff 作为强信号 |
| 引用（隐式） | 后续堆肥命中旧洞察 | 追溯性营养（见 02 §7 后见之明） |

## 9.2 不变量

> **INV-12 反馈是事件不是评分**：所有反馈以事件形式进入 bed_events，永不要求用户「给 AI 打分」。反馈延迟到达（用户三天后才点 ⭐）也按事件时间正确归因。

# 10. 本文关键决策汇总

| # | 决策 | 理由 |
| --- | --- | --- |
| D1 | Insight 是命题级单元，非长文 | 检索、引用、反哺营养都需要原子粒度 |
| D2 | Topic 系统涌现，用户永不创建 | Principle 01 数据层落实 |
| D3 | Agent 是数据（Prompt 卡 + 生态属性） | 增殖/融合/休眠 = 记录操作，工程可行 |
| D4 | Bed 事件溯源 + 物化快照 | 时间序列分析是长期愿景的基础 |
| D5 | 堆肥产物 JSON 为真源，MD 为视图 | 溯源、反馈、营养计算都需结构化 |
| D6 | 面包渣原文永存，永不压缩 | 与 ACP 的关键差异：存储廉价，思想珍贵（见 06） |
| D7 | 关系边只在堆肥中自然断言 | 控制复杂度，守住 v0.1 边界 |
| D8 | 「我不同意」不惩罚 Agent | 防谄媚循环，保留认知多样性 |
