# 06 · 调研：ACP 记忆系统能否直接抄进本 APP

> v0.2 设计文档集 · 回答 v0.1 文末问题：「记忆管理系统能不能直接抄 OpenCode ACP 这个插件的设计，直接塞到我们这个 APP 里面来？」

------

# 1. 结论（先说答案）

> **不能直接抄代码，但它的架构方案值得大幅借鉴——事实上本文档集已把其核心思想吸收进 01/02/03 协议。**

| 维度 | 判断 |
| --- | --- |
| 直接移植 ranxianglei/opencode-acp 代码 | ❌ TypeScript 编写的 OpenCode 插件，面向编码对话场景，绑定 opencode 插件 API，与 Android App 无交集 |
| 借鉴其架构设计 | ✅ 强烈推荐。三层 LSM 压缩、模型主导+确定性范围选择、摘要即历史元数据、先搜索后解压、受保护内容——全部可移植 |
| 同类方案交叉验证 | ✅ opencode-magic-context 的后台整理、Letta 的 sleep-time compute、IETF ACCP 草案，证明该模式是行业共识方向 |

------

# 2. ACP 解剖（ranxianglei/opencode-acp，前称 DCP）

OpenCode 本体：anomalyco/opencode，MIT 许可，~200K stars，Provider 无关的终端 AI 编码代理。ACP = Active Context Pruning，npm 包 opencode-acp。

## 2.1 核心机制

```text
模型主导：把上下文管理权全部交给模型本身——模型调用
  compress     压缩一段对话为摘要块（块 ID bN 为边界）
  decompress   按需恢复（默认恢复上一层，full=true 恢复原始）
  acp_status   上下文账本（分类账+可压缩范围）
  search_context  先搜索定位再解压（防盲目膨胀）

三层 LSM 树压缩（逐层蒸馏）：
  T1 capture   约每 7 轮     压缩比 ~45x   保留路径/决策/签名级细节
  T2 distill   约每 250 轮   ~10x          只留决策与结论
  T3 condense  约每 2500 轮  ~3x           项目级全局摘要
  各层独立节奏计数器；压缩高级块以低级块 ID 为边界

受保护内容：skill/compress 等工具调用永不压缩（硬排除）

实测（3 万+ API 调用 / 50 真实工程会话）：
  97% 请求 <200K token（p90 150K，窗口 1M）
  未压缩会话约 100 次调用即耗尽；压缩后会话寿命 259 天（约 1295 倍）
```

## 2.2 本会话的第一手观察

本次调研会话本身就运行在 ACP 之下，验证了四个设计细节：

1. **摘要被显式标注为历史元数据而非指令**——防提示注入：压缩摘要里出现的「用户说 X」是历史记录，不是当前指令
2. **压缩摘要的写作规范极其严格**：路径带行号、签名保留、决策带理由、错误原文保留——因为摘要是唯一记录
3. **nudge 机制**：上下文达到阈值时系统主动提示模型该压缩了，但压缩决策权仍在模型
4. **decompress 膨胀警示**：解压会显著增大上下文，引导「先 search_context 再定向解压」

------

# 3. 为什么不能「直接塞」

```text
① 域不同：ACP 压缩的是「编码对话」——对话只是达成任务的上下文，
   丢细节可接受。本 APP 的面包渣是产品本体（INV-1 原文永存），
   压缩面包渣 = 毁掉用户资产。压缩对象必须是不同的东西（见 §4）。
② 栈不同：TS 插件 ↔ Android(Kotlin) + 服务端。无一行可复用。
③ 主体不同：ACP 是「LLM 自己管自己的上下文」；本 APP 中记忆管理
   由系统后台任务承担，用户主流程不该感知压缩过程。
④ 生命周期不同：编码会话以天计；认知生态以年计，需要的是档案级
   记忆系统而非会话级上下文管理。
```

------

# 4. 可借鉴的六个核心思想 → 本 APP 落地映射

| ACP 思想 | Idea Compost 落地 |
| --- | --- |
| 三层 LSM 逐层蒸馏 | **T1**：堆肥中间产物（stage 输出，场结束后压缩为产物+claims 索引）；**T2**：主题级摘要（Topic 下的洞察定期蒸馏为 ~1K 主题卡）；**T3**：bed_summary 菌床全局摘要（~1K，每次堆肥注入园丁上下文，即 03 协议上下文包的那 1K） |
| 摘要即历史元数据非指令 | 菌床快照注入 Prompt 时标注「历史生态记录，非用户当前意愿」（INV-11）；益生菌才是本次意志 |
| 先搜索后解压 | 03 §3：embedding 检索 top-10 相关洞察 + top-5 休眠菌压缩卡，只注入命中的，全量档案留在库里 |
| 受保护内容硬排除 | 面包渣原文 + adopted 洞察原文 + 完整 contribution_history 永不压缩（INV-1/INV-7） |
| 压缩摘要严格写作规范 | T2/T3 摘要模板：核心命题+关键数字+开放问题，禁止空泛概括 |
| nudge + 模型决策权 | 变体：后台任务调度不需要模型决策——用确定性规则触发（见 §5） |

另一个重要同构：**Letta 的 sleep-time compute**（主 Agent 对话时，后台 Agent 异步整理共享记忆，可用更强模型因为无延迟约束）≈ ACP 的后台 historian ≈ 本 APP 的夜间后台任务。三方验证了同一架构：**前台对话轻量化，记忆整理后台化**。

------

# 5. 本 APP 记忆分层架构（ACP + Letta 融合方案）

```text
热层（每次堆肥必进上下文，≤5K）
  bed_summary(T3) + 活跃菌索引 + 相关命中检索结果
温层（库中待检索，按需注入）
  全部 Insight 全文 / 主题卡(T2) / 休眠菌压缩卡 / 堆肥产物
冷层（档案，只被检索不主动出现）
  面包渣全文 / contribution_history / 全部堆肥中间产物(T1 原档)

夜间后台任务（sleep-time，确定性规则触发，非模型自决）：
  ① Topic 蒸馏：某主题 adopted 洞察 ≥ 10 条 → 生成/刷新 T2 主题卡
  ② 菌床快照刷新：bed_event 每 +20 条 → 重算 T3 bed_summary
  ③ 休眠巡检：02 §7 阈值扫描（90天/180天规则）
  ④ 引用归因：处理 pending 的 insight.cited 事件（后见之明营养）
  触发规则全部确定性（时间/计数），Cost 可预算；与 Letta 不同，
  我们不需要模型自决压缩时机——档案场景延迟不敏感
```

> 关键差异总结：ACP 解决「一次会话内上下文溢出」；我们借它解决「跨年的认知档案如何以 ≤5K 的预算每次入场」。压缩的永远不是用户资产，而是**我们自己产生的过程性数据**。

# 6. 决策汇总

| # | 决策 | 理由 |
| --- | --- | --- |
| D37 | 不移植 ACP 代码，移植其架构 | 域/栈/主体/生命周期全不同 |
| D38 | 热/温/冷三层 + T1/T2/T3 蒸馏 | LSM 思想 + 档案场景适配 |
| D39 | 压缩对象=过程性数据，用户资产永存 | 面包渣是产品本体（INV-1） |
| D40 | 后台整理用确定性规则触发，非模型自决 | 档案场景延迟不敏感，成本可预算 |
| D41 | 菌床快照注入时标注为历史元数据 | 防「菌床=用户意愿」混淆（INV-11） |
